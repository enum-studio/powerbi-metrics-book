# The VM deploy guide, followed on a stand-in VM

A record of one run of `apps/docs/src/content/docs/deploy/vm.md` (issue i-vx66). Date: 2026-10-26, by the stand-in's clock. Build: `build/v1` at `e197028db74323d9cc42ca8b495f85e96468957d`, version 0.1.0, nothing published yet.

## The stand-in

- A privileged Ubuntu 24.04.5 LTS container (arm64, Docker Desktop host), name `pbmb-vmrun-a4acdc7c`, run with `--privileged --cgroupns=host`, 5 GB memory limit, hostname `pbmb-vm`. Volumes `pbmb-vmrun-a4acdc7c-docker` (`/var/lib/docker`) and `pbmb-vmrun-a4acdc7c-containerd` (`/var/lib/containerd`). Docker inside it is its own daemon.
- Its base image `pbmb-vmrun-a4acdc7c-base` is `ubuntu:24.04` plus what a cloud image has before an administrator logs in: systemd as init (`systemd`, `systemd-sysv`, `dbus`), `sudo`, a login user `ubuntu` with passwordless sudo, `iproute2`, `python3`, `ca-certificates`. After the container started, `/usr/sbin/policy-rc.d` was removed (the container image blocks starting services on install, a cloud image does not have it) and `ufw` was installed (Ubuntu cloud images ship it; the guide does not install it). Not installed beforehand: `curl`, `git`, Docker, `pipx`, `rclone`, `age`.
- The first container failed at step 7 (see "First attempt"). The log below is the second container, started from nothing, running steps 2 to 10 again with the guide as fixed so far.
- Each guide command ran as the `ubuntu` user in a login shell, the way the guide says. The setup screen was driven through the API by a script adapted from `apps/api/e2e/end-to-end.e2e.ts` and `browser.ts` (run in a throwaway `node:24-slim` container sharing the stand-in's network, so it reaches `https://metrics.example.com` and the mock at `127.0.0.1:3001` as a browser on the VM would).
- Host name: `metrics.example.com`. The stack ran on `compose.yml`, `compose.caddy.yml` and `compose.mock.yml`.

## The four deviations

The issue allows three. A fourth was forced by the same cause (nothing is published or tagged yet); it changes where files come from, not what the guide's commands do.

1. **Image.** Built on the host (`docker build -f apps/api/Dockerfile --build-arg GIT_SHA=<HEAD> -t powerbi-metrics-book:vmrun-a4acdc7c .`, and the mock from `packages/powerbi-mock/Dockerfile`), moved with `docker save` and `docker load`, then tagged inside as `ghcr.io/enum-studio/powerbi-metrics-book:0.1.0` (and as `powerbi-metrics-book:sample` and `powerbi-metrics-book-mock:sample`, the names `compose.mock.yml` uses). The digest survived the save and load: `sha256:42620e58011ef111b8c56c1f46328aca16f1cf6b96552bb2716d257256310290`. Consequence: this wheel has no released digest, so `pbmb init` refused to run and was given `--image ghcr.io/enum-studio/powerbi-metrics-book:0.1.0@sha256:42620e58...` as its own error message says. A released `pbmb` needs no flag.
2. **CLI.** `uv build --package powerbi-metrics-book --wheel` on the host, copied to `/tmp` in the stand-in. The guide's install command ran with the wheel's path where `"powerbi-metrics-book==$PBMB_VERSION"` stands.
3. **DNS and certificates.** `127.0.0.1 metrics.example.com` in the stand-in's `/etc/hosts`. One line, `tls internal`, added to the Caddyfile's site block in `/srv/pbmb` (not in `deploy/vm/Caddyfile`). Caddy's root certificate (`/data/caddy/pki/authorities/local/root.crt`, copied out with `docker compose cp`) was added to the stand-in's system store with `update-ca-certificates`; `pbmb` uses Python's own bundle, so it ran with `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt`.
4. **Release files.** Step 5 and step 9 fetch from GitHub at the commit of tag `v0.1.0`. The repository is private and the tag does not exist (`git ls-remote` stopped with `could not read Username for 'https://github.com'` and printed no commit). The files of `deploy/vm/` were served from a Python HTTP server on `127.0.0.1:8000` in the stand-in, copied from this branch at `e197028` (the same files as `build/v1`), except that `compose.caddy.yml` was replaced once by the version of fix 5, the one committed at `1d97d97`, and `base` was set to `http://127.0.0.1:8000/deploy`. Every `curl` in the guide ran unchanged after that.

Also outside the guide, as the issue directs: the stack points at the Power BI mock (`compose.mock.yml` copied into `/srv/pbmb`, `COMPOSE_FILE=compose.yml:compose.caddy.yml:compose.mock.yml`), and the backup uses local folders for the two buckets (below).

## First attempt

The first container had only `/var/lib/docker` on a volume. `docker compose up` failed to pull: `failed to convert whiteout file "etc/alternatives/.wh.pager.1.gz": operation not permitted`, and `pbmb check` failed the same way (`failed to mount ... overlay ... invalid argument`), because Docker 29's containerd store keeps images in `/var/lib/containerd`, on the container's own overlay filesystem, and overlay does not nest. A stand-in fault, not the guide's. The second container mounts a volume at `/var/lib/containerd` too. A later harness mistake: the host-built image first lacked `GIT_SHA` (the Dockerfile takes it as a build argument) and the `api` exited with `GIT_SHA is not set`; it was rebuilt with `--build-arg GIT_SHA=<HEAD>` and the deployment started again from `pbmb init`.

## Fixes to the guide

All in `apps/docs/src/content/docs/deploy/vm.md` unless noted.

1. **Step 4 (failed), and Upgrading.** `pbmb` needs Python 3.13 (`requires-python = "==3.13.*"`), Ubuntu 24.04 has 3.12, and `pipx install powerbi-metrics-book` stopped. Step 4 now installs `uv` with `pipx` and installs `pbmb` with `uv tool install --python 3.13`, which fetches Python 3.13. It sets `PATH` in the same shell, because `uv` was `command not found` right after `pipx install uv` (`~/.local/bin` is not on the path until a new login), and because a new shell would lose `PBMB_VERSION`, which steps 5 and 9 use. Upgrading uses `uv tool install --force --python 3.13`. Step 10 names the same command for the reader's own machine.
2. **Step 3 (not seen in the run).** `ufw enable` asks to confirm when it may cut off SSH. The stand-in has no sshd and showed no prompt; the sentence tells the reader to answer `y` because 22 is open.
3. **Step 5.** `git ls-remote` printing nothing was not explained, and the `curl` commands would then fail on a broken address. The guide says what a good result looks like and what an empty one means, and that step 9 needs `$base` from this shell.
4. **Step 6 (failed).** `dig` is not installed on Ubuntu Server. The check is now `getent ahostsv4 metrics.example.com | head -n 1`, which needs nothing installed.
5. **`deploy/vm/compose.caddy.yml` (failed on the second `docker compose up`).** `caddy-volumes` has only `CHOWN`. Caddy creates its own directories mode 0700, so on every start after the first, `chown -R` could not open them: `chown: /data/caddy/pki: Permission denied`, exit 1, `service "caddy-volumes" didn't complete successfully`. Step 7 passed only because the volumes were new; every later `docker compose up -d --wait` (the restart after a rotation, Upgrading, Restoring) would have failed. Added `DAC_READ_SEARCH` to that service's capabilities and said why in the comment. After the change, two `up -d --wait` in a row exit 0 and `caddy-volumes` exits 0.
6. **Step 9.** `age-keygen` runs on the other machine, and the guide never said how to get age there; it names `brew install age` and `sudo apt install age`.

## Not changed, for others

- `apps/cli`: `requires-python = "==3.13.*"` is why fix 1 is needed. A wider range would let `pipx` work on Ubuntu 24.04 once `pbmb` supports 3.12; that is the CLI's decision.
- `apps/api/e2e/end-to-end.e2e.ts` calls `pass("what_to_sync")` with an empty body; against this stack that answered `This check has not run yet`. Worth a look by whoever owns the e2e test: `scripts/dev-stack.mjs` sends `start_check: true`.
- Not exercised: Let's Encrypt (the run used Caddy's internal CA), real S3 buckets with Object Lock, `ufw` with a live SSH session, a released image and a PyPI package, a real Entra tenant.
